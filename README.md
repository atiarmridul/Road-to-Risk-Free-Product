<details>
<summary><strong>“My interview is soon.”</strong></summary>

Go directly to the [Interview Preparation Hub](03-interview/README.md).

- Practise aloud rather than reading silently.
- Use authentic examples and never claim a tool or result you cannot explain.

**Ready for the interview when:** You can give a focused two-minute technical answer and a three-minute scenario answer with context, action, trade-off, result, and learning.

</details>

## Run a focused study session

Use this repeatable 45-minute loop:

```text
5 min   Recall what you already know
20 min  Learn one focused concept
15 min  Apply it to an example or exercise
5 min   Record one insight, one gap, and one next action
```

<details>
<summary><strong>Open the session checklist</strong></summary>

- [ ] I selected one topic—not an entire folder.
- [ ] I wrote what I already knew before reading.
- [ ] I created an example, test, query, checklist, or script.
- [ ] I explained the topic aloud without copying the definition.
- [ ] I identified one limitation or trade-off.
- [ ] I chose the next specific action.

</details>

## Progress checkpoint

Copy this checklist into an issue, notebook, or personal progress file. GitHub does not save checkbox changes made only while viewing the README.

- [ ] I can explain the SDLC and the tester's role in each stage.
- [ ] I can design positive, negative, boundary, and risk-based tests.
- [ ] I can write a reproducible, evidence-based defect report.
- [ ] I can validate an API response beyond its status code.
- [ ] I can verify relevant database state safely.
- [ ] I understand unit, integration, contract, and E2E test boundaries.
- [ ] I can decide what should and should not be automated.
- [ ] I can build and debug one small automation suite.
- [ ] I can interpret essential performance and reliability signals.
- [ ] I can communicate release risk without reducing quality to a pass percentage.
- [ ] I can answer technical questions with examples and trade-offs.
- [ ] I can describe my real contribution without exaggeration.

<details>
<summary><strong>How do I know I truly understand a topic?</strong></summary>

You should be able to:

- explain it without copying its definition;
- give a realistic example and counterexample;
- identify the risk it addresses;
- state what it does **not** prove;
- compare it with a nearby concept;
- apply it to an unfamiliar feature;
- describe at least one trade-off or failure mode.

</details>

## Practice prompt generator

Pick one item from each column and answer the combined prompt.

| Product area | Quality concern | Deliverable |
| --- | --- | --- |
| Login | Security | Risk list |
| Checkout | Data integrity | Test scenarios |
| Search | Performance | API checks |
| File upload | Reliability | Boundary cases |
| Notifications | Integration | Defect report |
| User profile | Accessibility | Automation decision |

Example: **“For checkout data integrity, create API checks.”** Change the combination each day to practise applying concepts instead of memorizing answers.

## Repository principles

- One primary topic per Markdown file
- Lowercase kebab-case for new paths
- Practical examples before unnecessary theory
- Explicit risks, limitations, and trade-offs
- Markdown notes as the maintained source; PDFs as supplementary material
- No credentials, private environment files, logs, or generated reports
- Honest interview claims grounded in real experience
